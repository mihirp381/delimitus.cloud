## 001 Cloud and runtime

**Amendment pending (decision 025, 2026-10-03).** The choice of GCP and Cloud Run gen2 stands. Pending: no warm prod instances, no internal load balancer, one external Application Load Balancer per cell (SSC-088). The $199.37 and $9.86 figures below price the retired design. Nothing below is rewritten until SSC-086 reports.

Choice: Google Cloud. Each customer cell is its own project, with apps on Cloud Run gen2 in `us-central1`.
- Apps attach to a custom VPC with Direct VPC egress (`--vpc-egress all-traffic`). The VPC denies all egress except to the cell's egress proxy. A private Cloud DNS zone answers NXDOMAIN for the canary zone. Cloud NAT holds the cell's one fixed outbound IP.
- Ingress is `internal-and-cloud-load-balancing` behind one regional internal Application Load Balancer (serverless NEG per app). The `run.app` address is never used.
- Apps run as a service account with no roles.
- The kill switch moves 100 % of traffic to a tombstone revision (cut-off 2.3 s); deleting the service (1.6 s) is the fallback. Removing the invoker binding (80 s) and swapping the load-balancer route (142 s) are too slow and are not used.
- Prod environments keep one instance warm (`min-instances 1`, about $9.86 a month per app at the idle rate); preview environments scale to zero.

Reason: GCP passes every security row: egress, DNS exfiltration, machine token, peer isolation, public ingress, header passthrough and the 30-minute WebSocket / 10-minute SSE holds. It has the fastest cut-off. The empty cell costs $199.37 a month, under A7's $450. Cloud Build worked with no support ticket. IAM deny policies can block secret reads at the org level. Delimitus already runs on GCP, so the team knows its IAM, billing and failure modes.
- AWS also passes every security row, and its empty cell is cheaper ($173.71). Fargate has no request-driven scale-to-zero, though: starting from zero took 25 to 125 s, so every app needs a warm task, even in preview. AWS offered no advantage that outweighs the team's GCP experience.
- Azure fails peer isolation: apps in one Container Apps environment reach each other. It has no user-authored deny on secret reads, and ACR Tasks is blocked until a support request. Its empty cell costs the most ($362.02), and its cold starts were the slowest (static 25 s, API 24 s, Streamlit 39 s at p50).

Known gap: no candidate meets the cold-start targets from zero. GCP p50 was 4.5 s static, 8.2 s API and 22.3 s Streamlit; Fly's floor for the same images was 2.2, 5.8 and 4.3 s. Warm prod instances cover production; previews show the cold start. Worth measuring before the Cloud Run driver ships: startup CPU boost, and cold start without Direct VPC egress (the gap between the container-start metric and first byte is 1 to 15 s).

Reverse if: warm-instance cost per app pushes a typical cell over A7, or a customer needs cold starts GCP cannot meet with startup CPU boost. Also reverse if an IAM deny policy on `secretmanager.versions.access` does not hold when tested, or tombstone-revision cut-off exceeds 10 s under load. AWS is the fallback: it passed the same security rows, and the runtime driver (decision 014) hides the runtime behind one protocol.

## 002 Login vendor and directory join key

Choice: WorkOS for SSO (SAML) and Directory Sync. Command-line login was AuthKit's device flow; amended below.
- An SSC user is keyed on the directory user (`(issuer, subject)` with the directory `idp_id`), never on email.
- A login joins its directory user by SSO `idp_id` equal to directory `idp_id`. Okta passes: the `00u…` user id is in both, and it survived an email change.
- Google Workspace SAML sends the email as `idp_id`, so a Google login joins by a unique lower-cased email match against the synced directory, and the fallback design in `spikes/loginproof/RESULTS.md` applies: an unmatched login gets no groups and lands in an admin `Unlinked logins` list; a link, once made, is stored and audited.
- The SSO email and the directory email can disagree (Okta sent the old address after a change), so email is display only.
- WorkOS does not revoke refresh tokens or end sessions when a directory user is removed (measured: still refreshing 11 minutes after a Google suspension). On `dsync.user.updated` to `inactive` and on `dsync.user.deleted`, SSC ends its own sessions and revokes the user's WorkOS sessions (`POST /user_management/sessions/revoke`).
- Google Workspace removes a suspended user from the directory instead of marking them `inactive`, so both events are handled. WorkOS polls Google (docs: about every 30 minutes; observed about ten), so the 5-minute lockout in SSC-019 counts from the directory event, not from the admin's click.

Reason: WorkOS was the only vendor in scope. The two tenants measured cover the join-key good case (Okta) and the bad case (Google), and the fallback design keeps Google usable without a stable key. Staging is free; production connections cost $125 each a month for the first 15.

Known gaps: Entra ID was not measured (founder decision 2026-09-30); whether its OIDC `idp_id` is the pairwise `sub` or the tenant `oid` is still Unknown. Okta deactivation, revocation and SCIM push latency were not measured. WorkOS data residency is Unknown; ask WorkOS before promising an EU region.

Reverse if: an Entra tenant joins neither by `idp_id` nor by the `objectidentifier` claim; a buyer needs a data region WorkOS cannot provide; or revoking WorkOS sessions from the directory event does not stop a refresh.

Amendment 2026-10-01 (SSC-019, decision 024): SSC does not use WorkOS User Management or AuthKit. The measured gap above (WorkOS refreshes after a suspension) made WorkOS sessions a second place to revoke; instead SSC calls only `/sso/authorize` and `/sso/token`, issues its own sessions and tokens, and runs its own RFC 8628 device flow at the auth host. Revocation on deactivation is SSC's alone, so there are no WorkOS sessions to revoke. Every other choice above stands. Measured in SSC-002 and relied on: the Google directory `idp_id` is Google's numeric user id, not the email.

## 003 App database connection string form

Choice: every app database gets one URL, and the same values as separate `PG*` variables.
- `DATABASE_URL=postgresql://app_<id>:<password>@<host>:<port>/app_<id>?sslmode=verify-full&sslrootcert=<absolute CA path>`
- Also `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGSSLMODE`, `PGSSLROOTCERT`, for frameworks with no URL parser (Django).
- The cell agent creates the database with the Cloud SQL Admin API `databases.insert`. Roles and grants go through `executeSql`, in the four-step order in `spikes/appdb/RESULTS.md`. Grants run before `REVOKE CONNECT ... FROM PUBLIC`, because afterwards the cell agent can no longer connect.
- `executeSql` callers check `status.code`, not only the HTTP code, because SQL failures return HTTP 200.

Reason: psycopg, asyncpg, node-pg, drizzle and Prisma 7 (through its adapter) all accepted the URL as given and rejected a wrong CA. Django needed the parts. On Cloud SQL, creation from the cell agent took 1.67 to 2.1 s. An identity with no roles got HTTP 403, and no app role could connect to another app's database. `executeSql` runs semicolon-separated statements in one transaction and cannot run `CREATE DATABASE`, hence `databases.insert`.

Reverse if: a pilot framework can use neither the URL nor the `PG*` parts. Also if Cloud SQL `executeSql` limits (30 s, 10 MB) block role management; the fallback is a Python connector over the cell's private endpoint, already needed for anything longer or larger.

**Amendment pending (SSC-040, 2026-10-03).** Built and tested locally against a postgres:18 set up the way Cloud SQL is, not yet run live (SSC-086 T5). The cell agent (`ssc_agent.app_database`, over `executeSql` with `autoIamAuthn` and `databases.insert`) makes, per app environment, `app_<id>_owner` (no login, owns the database), `app_<id>` (login, `CONNECTION LIMIT 2`, member of the owner, every session in its database `SET role` to the owner) and the database `app_<id>`, with nothing for `PUBLIC` on the database or its `public` schema. Before it creates a role it counts the `app_*_owner` roles under an advisory lock and refuses one past `(max_connections - reserved - 2) / 2` (ten on `db-f1-micro`'s 25, previews included) with `DB_TIER_FULL`; nothing is created. It makes the password itself, writes `DATABASE_URL`, `PGPASSWORD` and the server CA (`DATABASE_CA`) as new versions in the cell's Secret Manager, then sets a SCRAM verifier, so no statement carries the password and the control plane gets back the address and version numbers only (`ssc.app_database`, revision `0022_app_databases`; `secret_ref` rows audited `secret.bound`/`secret.rotated`). The deploy job asks for the database the first time a `postgres = true` deployment runs, outside its transaction, and pins the versions like any secret. The host is the instance's DNS name (else its private address); the CA is mounted at `/etc/ssc/db-ca.crt`; the `PG*` parts other than `PGPASSWORD` are plain variables. A stateful environment runs at most one instance with a pool of one connection; the second connection of its limit is kept for the incoming revision during a deploy or rotation (the old revision still serves) and for a migration run at start. Rotation: `POST /v1/apps/{app}/environments/{env}/database/rotate`, then a deployment of the live release. Freeing a place (SSC-042): the agent's `POST /v1/databases/drop` stops the login role, drops the database (`databases.delete`) and both roles, and deletes the three database secrets; it is safe to re-run and is `409 SERVICE_LIVE` while the environment's Cloud Run service exists and is not stopped. Nothing in the control plane calls it yet: no environment or app delete exists. The kill switch keeps data in both modes, so it never drops (SSC-025); the caller belongs with the database quotas and export in SSC-080, or a later environment delete. Nothing below is rewritten until SSC-086 T5 passes.

## 004 Domains and app hosts

**Amendment pending (decision 025, 2026-10-03).** The host rule stands. Pending: the wildcard certificate is a Certificate Manager certificate with DNS authorisation, one per cell (SSC-088). Nothing below is rewritten until SSC-086 reports.

Choice: `delimitus.com` carries the platform hosts (`api.`, `auth.`, `keys.`, `console.`). Apps are served on `delimitusapps.com`, already registered and used for nothing else; `delimitus.app` is not used. The API reads it from `SSC_APPS_DOMAIN` (default `delimitusapps.com`; tests use `apps.test`) and refuses to start on a value that is not a lower-case DNS name of at most 186 characters. Every app environment has one host (`ssc_shared/hosts.py`):

- prod: `<slug>.<cell label>.<apps domain>`; preview: `<slug>--preview.<cell label>.<apps domain>`.
- The cell label is the org's `ssc.org.cell_label`: random, opaque, `^[a-z][a-z0-9]{7,15}$` (twelve consonants from revision 0011 on), never the customer's name, set for every org when it is created. One wildcard certificate `*.<cell label>.<apps domain>` covers every host of an org.
- A slug matches `^[a-z]([a-z0-9-]{0,38}[a-z0-9])?$`, has at least 3 characters (so no label has `--` in positions 3-4, which IDNA2008 reserves, and `xn` never makes `xn--preview`), has no `--` (so no leading `xn--`), and is not reserved: `www`, `api`, `auth`, `login`, `console`, `admin`, `status`, `static`, `keys`, `ssc`, `mail`. `POST /v1/apps` refuses a slug that breaks a rule with `422 VALIDATION_FAILED` from the model, before any insert. The database CHECK still refuses `--` on its own.
- `app_host` and `app_origin` build a host and its `https://` origin, and refuse anything the rule refuses. `parse_app_host` returns the (slug, environment, cell label) of a host, or nothing for any host the rule would not produce: the caller lower-cases it and drops the port first. The round trip, the one-host-per-(slug, environment) property and the DNS limits (63 per label, 253 per host) are property tests.
- `EnvironmentOut.url` is the environment's origin. It is null only for a slug stored before this rule refused it.

Reason: an app under `delimitus.com` would share a site with the login and API hosts, and would receive the live Delimitus product's `delimitus.com` cookie (tickets §2 SSC-006). Opaque labels keep certificate transparency logs from listing customers. A flat first label with `--preview` keeps every host one level under the org wildcard, and reserving `--` means a preview host can never be another app's prod host. Refusing `xn--` rules out punycode lookalikes. The reserved words keep names such as `login.<label>` from looking like platform pages.

Reverse if: the founder chooses per-app labels (lane option B: an `app.host_label` column, a lane A migration, the same module with a different input), or customer domains arrive (Phase 2: a customer-dedicated registrable domain, never a subdomain of theirs).

## 005 The seven decide-once rules

Choice: from the build path, fixed before code:
1. Every customer gets their own cloud project (decision 021). Our shared system holds only the bookkeeping.
2. Apps live on `delimitusapps.com`, never on a customer's domain and never under `delimitus.com` (decision 004). Cookies never cross between apps.
3. Sharing rules, data permissions, timers and secrets belong to the environment, not to a release. A rollback never restores an old permission.
4. The app learns who the user is from one signed note on every request, one header, one format (decision 010).
5. Every action gets a line in a log that cannot be quietly edited (decision 012).
6. Only a person approves. An AI agent can only ask; the service enforces it and records the approver (decision 016).
7. All new backend code is Python. We buy compute, login, image building, logs and secret storage instead of writing them.

Reason: each rule is expensive to retrofit. Isolation, cookie scope, permission lifetime, identity format, audit integrity and the approval boundary all shape the schema and the contracts. Rule 7 keeps a small team on one language and off infrastructure it cannot staff.

Reverse if: a paying customer requires their own domain (rule 2; a separate security design), or a bought service cannot meet a stated requirement and no other vendor can (rule 7, for that one service only).

## 007 Toolchain pins and the 7-day rule

Choice: uv 0.12 and Python 3.14 only. Pins: FastAPI 0.141, Pydantic 2.13, SQLAlchemy 2.0.54, psycopg 3.3, Alembic 1.20, Procrastinate 3.10, PyJWT 2.15, Typer 0.27 and httpx2 2.13 (the repo README keeps the full list).
- No dependency may be younger than 7 days. uv enforces it with `exclude-newer` in `pyproject.toml`. CI checks it with `tools/lock_age_check.py`, and with `tools/npm_lock_age_check.py` for the console's `package-lock.json`.
- An exception needs a reason and an expiry in `docs/lock-exceptions.toml`.
- CI runs ruff, pyright, import-linter, deptry, zizmor, gitleaks, the lock-age checks, the OpenAPI checks and pytest.
- `gates/run_gates.py` plants one violation per gate and CI fails if any gate lets its violation through.

Reason: a 7-day delay keeps a freshly published malicious release out of the lock file. The planted-violation gates prove each check still bites. One Python version and exact pins keep the three lanes' environments identical.

Reverse if: a security fix must land sooner than 7 days (add an expiring exception, never drop the rule). Or Python 3.15 is released and every pinned package supports it (then bump in one change).

## 008 Job queue

Choice: Procrastinate 3.10.0, core package only (psycopg connector, no SQLAlchemy extra), on the control-plane Postgres 18.

Reason: the four SSC-004 crash tests pass in CI against a `postgres:18` container. Deferring with `task.configure(connection=conn)` rides the caller's transaction, so a job and its data row commit or roll back together. `queueing_lock` refuses a duplicate with `AlreadyEnqueued`. A worker killed with SIGKILL mid-job leaves the job in `doing` with a stale worker heartbeat; `job_manager.get_stalled_jobs(seconds_since_heartbeat=...)` finds it and `retry_job` returns it to `todo`, after which a fresh worker runs it again (attempts becomes 2). A duplicate defer inside `conn.transaction()` (a savepoint) leaves the outer transaction usable; without the savepoint the connection is in `InFailedSqlTransaction`.

Rules this imposes on SSC-016 and every reconciler: defer through the caller's connection, never a second connection; give every idempotent job a `queueing_lock`; wrap each defer in a savepoint; run a periodic task that sweeps `get_stalled_jobs` and retries, because 3.10 has no built-in `retry_stalled_jobs`; set `update_heartbeat_interval` and `stalled_worker_timeout` on workers and keep `seconds_since_heartbeat` above the heartbeat interval.

Reverse if: a later Procrastinate release drops the psycopg connector, or a job needs exactly-once side effects outside Postgres (then DBOS or an outbox pattern is re-evaluated).

## 009 Control database

Choice: one Postgres 18 database for the control plane, schema `ssc`, with customer separation enforced by the database itself. Full rules in `packages/ssc_control/src/ssc_control/db/README.md`; the list of PL/pgSQL functions in `PLPGSQL.md` there; the personal-data inventory in `PII.md` there.

- Every table carries `org_id`; foreign keys are `(org_id, id)` pairs. Row-level security is enabled and forced on every table in `catalog.TABLES` (19 today; `org_index` below is the one exception). `ssc.current_org()` raises SQLSTATE `SC001` when no org is bound; it never returns NULL.
- The bind is `set_config('ssc.org', <org id>, true)`, once per unit of work, in the transaction. Never per statement (Delimitus paid 5 to 7 round trips for that), never per session (a pooled-connection leak). A test refuses any non-transaction-scoped `set_config` in the package.
- Two roles. `ssc_migrate` runs Alembic and owns every object. `ssc_app` is the application: `NOBYPASSRLS`, explicit per-table privileges written in `catalog.APP_ROLE_PRIVILEGES`, nothing on `ssc.alembic_version`. No `GRANT ... ON ALL TABLES` (Delimitus `003_rls.sql:113` gave the app role DELETE on the migration ledger that way).
- Our SQLSTATE class is `SC`: `SC001` no org bound, `SC002` last admin, `SC003` owner not active, `SC004` release immutable, `SC005` audit row immutable, `SC006` truncate refused, `SC007` schedule deleted.
- PL/pgSQL is a bounded exemption from the Python rule: six functions today, limit ten, listed in `PLPGSQL.md` and enforced by a catalog test. Everything else is Python.
- Releases and audit rows are immutable: no UPDATE or DELETE privilege, plus triggers that refuse the owner too, plus TRUNCATE guards. One deployment in flight per environment is a partial unique index. A deployment's release and environment must belong to the same app (composite FKs through `app_id`).
- Approvals: `decided_via_agent` is `CHECK (= false)` and an approved request's decider must differ from its requester. Only a person approves, never the requester.
- Table names `user_account` and `user_group`, because `user` and `group` are reserved words in Postgres.
- Org creation is admin-first and atomic (`db.orgs.create_org`), seeding the audit head with a 32-byte zero genesis hash. The `org.created` audit row (seq 1, SSC-012) and the org's `ssc.org_index` row are written in that same transaction.
- Audit actions and actor kinds are closed lists: a CHECK in the database and a `StrEnum` in `ssc_contracts.audit`, with a test that they match. Adding an action is an expand migration.
- Alembic runs from Python (`ssc_control.db.upgrade`), no `alembic.ini`, version table in schema `ssc`, expand-then-contract. Revision SQL lives in `migrations/sql/` and runs through the raw psycopg cursor because PL/pgSQL bodies contain `%s`.
- Procrastinate's tables live in their own schema, `procrastinate` (revision `0006_procrastinate_orgindex`, wired by SSC-017; decision 014). They are not org-scoped and stay outside the RLS catalog check; the app role's privileges on them are explicit per table in `catalog.QUEUE_APP_PRIVILEGES`.
- Amendment 2026-09-29 (SSC-017, founder answer): `ssc.org_index` is the single unscoped table. Forced RLS makes a cross-org scan impossible, which is the point, but workers must find every org (reconciler tick, audit anchors, timer re-arm). The table holds `org_id` (primary key, foreign key to `ssc.org`) and `created_at`, nothing else, and has no RLS. `ssc_app` may `SELECT` and `INSERT` it, never `UPDATE`, `DELETE` or `TRUNCATE`; `create_org` inserts the row in the org's creating transaction, so an existing org is always discoverable and a rolled-back one never is. It is listed alone in `catalog.UNSCOPED_TABLES`, never in `catalog.TABLES`, so every rule stated over `TABLES` stays exception-free. Workers call `db.orgs.all_org_ids`, then do each org's work inside `bound_org`. No `BYPASSRLS` role and no `SECURITY DEFINER` function exist for this; a second unscoped table needs its own decision. Rejected: a `BYPASSRLS` sweep role with a column grant on `ssc.environment` (a second DSN and a role that can bypass RLS, for one column).

Reason: the product's central claim is per-customer isolation enforced at the data layer. Retrofitting RLS onto an existing schema is much harder than starting with it, and the Delimitus live test showed every footgun this closes (owner exempt under plain ENABLE, silent zero rows on a missing scope, over-broad grants, session-scoped binds). Tests in `packages/ssc_control/tests/test_control_db.py` attack the schema through raw SQL as `ssc_app` against a `postgres:18` container.

Reverse if: the control plane must shard across databases (then org routing replaces RLS as the first guard and RLS stays as the second), or the chosen cloud's managed Postgres cannot create non-superuser owner roles the way Cloud SQL does (then the two-role split is re-planned in SSC-013).

## 010 Identity note v1

Choice: apps learn who the user is from one signed header, `X-SSC-Identity`, and nothing else. Contract in `docs/contracts/identity-note.md`.

- Compact JWS, `alg` ES256 only, `typ` `ssc-id+jwt` required, `kid` required. Twelve claims and no others: `iss`, `aud`, `sub`, `iat`, `exp`, `org`, `app`, `env`, `role`, `groups`, `name`, `email`. `aud` is the app's exact origin as one string. `exp = iat + 300`, and a verifier refuses a longer life even when the note has not expired.
- `sub` is `usr_` or `sch_`, never an email. `name` and `email` are display strings and are absent on schedule notes. `role` is `builder`, `user` or `schedule`; `groups` holds at most 50 `grp_` ids and only the groups the app's sharing rule references.
- Both helpers (`ssc_app.identity`, `@delimitus/ssc-identity`) raise one exception with one code from a closed list of twelve, run the same checks in the same order, and pass the same 33 vectors in `conformance/identity_note/`. The Node helper has no dependencies (webcrypto), so a customer app inherits nothing from us.
- Keys: EC P-256 in cell Secret Manager, public JWKS at `https://keys.delimitus.com/<cell_label>/jwks.json` as a static CDN file with at most two keys during rotation (SSC-013 implements). The gateway is the only minter (`ssc_edge.identity_note`).
- Apps verify once per request and never mid-stream; revoking access ends open streams through the kill switch drain, not through token expiry.

Reason: the Delimitus design left end-user identity forwarding unspecified and header spoofing unaddressed (build plan §2, problem 3). Fixing the header, algorithm, type and claim set on day one, with vectors both helpers must pass, means the gateway, the data gateway, the CLI's agent pack and every customer app agree before any of them is finished. `typ` and single-string `aud` close the two classic JWT confusions (a token minted for something else replayed here; a note for app A accepted by app B). Names and emails ride along because the founder asked for them (tickets §9 question 8) and they are on the PII list.

Reverse if: a customer needs a non-JWT form (then v2 is added beside v1, never in place), or the cell's key store cannot hold P-256 keys (then the algorithm set is widened by a v2 `typ`, not by accepting more algorithms under v1).

Amendment (SSC-018, 2026-10-01): key storage. Decision 022 denies `secretmanager.versions.access` to every SSC identity in a cell, the gateway included, and no grant can undo a deny rule, so the signing key cannot live in cell Secret Manager. The gateway's keys (the identity signing keys and the session keys) are one JSON keyring, encrypted with a Cloud KMS key in the cell that only `ssc-gateway` may decrypt with (`cloudkms.cryptoKeyDecrypter` on that key alone). The ciphertext is set on the gateway service as `SSC_GATEWAY_KEYRING` and decrypted once at start (`ssc_edge.keys`). A plain keyring is accepted only when `SSC_ENV` is `dev` or `test`. The JWKS location and rotation are unchanged; publishing it was listed under SSC-013 but was not built, and moves to the cell wiring after SSC-017.
## 011 API conventions

Choice: one FastAPI application, `/v1` for people and their tools and `/internal/v1` for cell services, with the conventions below fixed before the first real endpoint. Full text in `docs/api/README.md`; code in `packages/ssc_control/src/ssc_control/api/`.

- Every refusal is an RFC 9457 problem with exactly seven members (`type`, `title`, `status`, `detail`, `instance`, `code`, `request_id`) rendered by one function. The catalogue (`ssc_contracts.errors.CATALOGUE`) holds fixed sentences per code; evidence goes to the log under the request id, never to the client. Codes today: `VALIDATION_FAILED`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `UNSUPPORTED_MEDIA_TYPE`, `UNAUTHENTICATED`, `FORBIDDEN`, `RATE_LIMITED`, `IDEMPOTENCY_KEY_REQUIRED`, `IDEMPOTENCY_KEY_REUSED`, `IDEMPOTENCY_IN_FLIGHT`, `PRECONDITION_REQUIRED`, `PRECONDITION_STALE`, `ALREADY_EXISTS`, `REFERENCE_NOT_FOUND`, `DEPLOYMENT_IN_FLIGHT`, `LAST_ORG_ADMIN`, `OWNER_NOT_ACTIVE`, `RECORD_IMMUTABLE`, `SCHEDULE_DELETED`, `INTERNAL`.
- Credentials are ES256 JWTs with `typ: ssc-api+jwt`, one audience per surface, verified against a configured JWKS. The `jti` is the credential id; rate limits and idempotency keys are scoped to it. A user credential on `/internal/v1` is `FORBIDDEN`.
- An optional `scope` claim narrows a credential (SSC-042, founder question D3). Absent: everything the subject may do. `preview`: the credential never touches production, for the GitHub Action before issued tokens (019); CI mints such tokens with `tools/dev_stack.py token --scope preview`. Any other value is `UNAUTHENTICATED`. The unit of work checks it before any handler: a path naming a prod `{environment_id}` is `FORBIDDEN` for every method, and any other change (not `GET`, `HEAD` or `OPTIONS`) is `FORBIDDEN` unless it is in `uow.PREVIEW_SCOPE_CHANGES`, today only the bundle upload, or is a share ask: `POST /v1/approvals` of kind `agent_share` or `widen_audience` whose body names an environment that is not prod (founder, 2026-09-29; asking changes nothing, another admin decides). So a route added later, promote included, is closed to such a credential until it names a preview environment or is listed. A route that names an environment changes only that environment.
- One org-bound transaction per request (`bound_org`), opened by a FastAPI dependency with `scope="function"` so it commits before the response is sent. Audit rows are appended inside it (`ssc_control.audit.append_event`, chain `sha256(prev_hash || canonical)` over sorted-key JSON, head locked `FOR UPDATE`).
- `Idempotency-Key` is required on every `POST` and claimed in the transaction through table `ssc.idempotency_claim` (revision `0002`, the 19th table, keyed by org, credential and key, RLS like the others). States: absent, claimed, settled. A duplicate blocks on the primary key until the first commits, then replays the stored status, body and headers with `Idempotency-Replayed: true`. Same key with a different body is `IDEMPOTENCY_KEY_REUSED`; a visible unsettled claim is `IDEMPOTENCY_IN_FLIGHT` and is never re-run. Only successful replies are stored; a refusal rolls the claim back.
- Sharing-rule edits (`PUT .../grants`) require `If-Match` equal to the environment's `grants_version`, returned as `ETag`. Missing: `428`; stale: `412`. The row is locked `FOR UPDATE` before the comparison; the edit is a diff (add and remove, each audited) and bumps the version.
- A deployment is an operation: `202` plus `Location: /v1/operations/{id}`; a second one in flight is `409 DEPLOYMENT_IN_FLIGHT` from the partial unique index.
- Rate limits are an in-process token bucket per credential with `Retry-After`. Settings are a frozen dataclass read from `SSC_*` environment variables; no settings library.
- `docs/api/openapi.json` is committed, rendered deterministically (sorted keys) and checked in CI; `tools/openapi_breaking.py` fails the lint job on a removed path, operation, response status or response property, a request property removed or made required, a changed type, a removed enum value or a new required parameter. The gate has a planted fixture like every other.
- Agent interface (SSC-048): an MCP server at `/mcp` on the same application, for agent credentials only (`agent: true` with a `client_id`). Its tools call `/v1` in process with the caller's bearer, so they add no authorisation, idempotency or audit code of their own; refusals are tool errors carrying the problem. Tools: `get_platform_requirements`, `get_org_deployment_policy` and `preflight` (SSC-093, decision 017), `list_apps`, `get_app`, `get_status`, `list_releases`, `rollback`, `deploy` (preview only), `request_share`, `request_connection`, `get_logs` (redacted, inside an untrusted frame, and off for agents when an org admin says so) and `set_secret` (takes no value; answers the `ssc secret set` command for the person); approving, promote, a secret's value, listing connections beyond those the caller may see (`get_org_deployment_policy` shows only those, decision 016 amendment SSC-093), the warm flag and the cell resource flags are absent on purpose. A deployment waiting on a one-time creation tells the agent to wait instead of retrying. Details in `docs/api/README.md`.

Reason: these are the things every client (CLI, Action, console, agents) will hard-code against, and they are cheap to fix now and expensive after the first external caller. Storing the reply with the claim is what makes "replay returns the first result" true byte for byte rather than "probably the same".

Reverse if: more than one API replica needs a shared rate limiter (then a store replaces the in-process bucket, keeping the header contract), or a client needs partial-failure detail beyond the fixed text (then a structured `errors` member is added to `Problem` as an additive change, never free text).

## 012 Audit log

Choice: every org has one append-only, hash-chained log in `ssc.audit_event`, written only by `ssc_control.audit.append_event` inside the transaction that makes the change. Code in `packages/ssc_control/src/ssc_control/audit/`.

- Canonical form ssc-audit-v1, frozen: a JSON object with exactly nine keys, `org_id`, `seq`, `at`, `action`, `actor` (`kind`, `id`, `via_agent`, `client_id`, `ip`), `target` (`kind`, `id`), `before`, `after`, `policy_decision_id`, encoded as `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)` in UTF-8. `at` is ISO 8601 with its offset (the writer uses UTC). No floats anywhere. No version key: its absence means v1; a v2 adds `"format": "ssc-audit-v2"` and v1 rows stay as written.
- Chain: `hash = sha256(prev_hash || canonical)`. Genesis: `create_org` seeds `audit_head` at seq 0 with 32 zero bytes and appends `org.created` as seq 1 in the same transaction (default actor `operator` / `system:create_org`). An append locks `audit_head` `FOR UPDATE`; unique `(org_id, prev_hash)` and `(org_id, hash)` make a fork unstorable.
- Views: `before` and `after` hold only the keys listed for the row's target kind in `audit/views.py`, as strings, integers, booleans, nulls or lists of strings. The one nested object is an `audit` row's `filters`, limited to the search filter names. The views name no personal data and no secret (a test checks them against `db/catalog.py`), so an erasure request never needs the log edited. A new target kind adds its view before its first audit call.
- Client IP: none is recorded until SSC-013/018 supply a trusted address (lead decision, 2026-09-29). `actor_ip` stays NULL and the canonical `actor.ip` is null. How a trusted address is kept later (in the chain or in an erasable side table) is decided with SSC-013; exports carry canonical bytes only while they hold no IP.
- Policy link: `uow.audit(..., policy_decision_id=...)` stores the `pol_` id of the decision that allowed the change, a foreign key to `ssc.policy_decision`, and it is inside the canonical.
- `verify(conn, org_id)` walks the chain from genesis in seq order and names the first broken link as a seq and a cause: `missing` (a gap, or a head beyond the last row), `prev_link`, `hash`, `fields` (the canonical is not v1 canonical JSON or disagrees with the row's columns) or `head`. `python -m ssc_control.audit verify --org <id>` runs it in a REPEATABLE READ transaction with `SSC_DATABASE_DSN`, prints `ok: ...` or `broken: seq N cause C`, and exits 0 or 1.
- Reading: `GET /v1/audit` pages newest first on a `before_seq` cursor, for active org admins with a user credential; operators are refused in MVP (no standing staff access). `GET /v1/audit/export?format=csv|jsonl` first commits an `audit.exported` row (`after`: format and filters), then streams oldest first from its own read-only REPEATABLE READ snapshot, so the export lists itself. Agent credentials are refused. `actor_ip` is never exported; CSV cells starting with `=`, `+`, `-`, `@`, tab or carriage return get a leading `'`; each JSON line adds `canonical` in base64 so a customer can recompute every hash offline.
- What it protects against: the application role cannot UPDATE, DELETE or TRUNCATE the log (no privilege, and triggers raising `SC005`/`SC006` refuse the owner too). A database superuser, or the owner with `session_replication_role = replica`, can still rewrite a row and recompute every later hash and the head; `verify` alone cannot see that, and anchors in the blob store do. Until the bucket retention lock (Step 5) stops anchors being rewritten, someone who can write both the database and the bucket can still rewrite history unseen.
- Anchors (A1b, revision 0011; `audit/anchor.py`): an anchor is the org's head `(seq, hash)` at one moment, stored as an object in the blob store and as a row in `ssc.audit_anchor` (append-only, `SC005`/`SC006`). The object, `ssc-audit-anchor/v1`, is canonical JSON in the chain's encoding with exactly seven keys: `format`, `org_id`, `seq`, `hash` (lowercase hex), `anchored_at`, `reason` (`daily` or `restore`) and `restored_to` (a restore anchor's restore point, otherwise null). Readers refuse any other shape, non-canonical bytes and objects over 4 KiB. Keys: `audit-anchors/<org>/<YYYY-MM-DD>.json` for a day's anchor, `audit-anchors/<org>/restore-<YYYYMMDD-HHMMSS-ffffff>.json` for a restore anchor.
- Writing: `write_anchor` holds the org's advisory lock `(12, hashtext(org_id))`, reads the head and `clock_timestamp()` in one statement, so `anchored_at` is never earlier than the head it names, then puts the object (bounded at 20 s) before it inserts the row, so a committed row always has its object. An object is never replaced: one already under the key is adopted when the chain agrees with it and refused (`AnchorConflictError`) when it does not, unless a later restore anchor supersedes it. Daily anchors add no audit event; the row and the object are the record.
- Daily job (`audit/jobs.py`): the worker's `audit:anchor_tick` runs at five past every hour, UTC, and defers one `audit:anchor` job for each org without the day's anchor (`queueing_lock` `anchor:<org>:<day>`). The day's anchor is therefore written at 00:05, or within an hour of a stopped worker coming back: hourly, because Procrastinate forgets ticks missed while no worker ran. Anchor jobs retry forever, 30 s doubling to at most an hour apart, because a missing anchor is a gap for an operator to see, not a job that gave up. With no blob store configured both do nothing. A new org gets its first anchor at the next tick; `python -m ssc_control.audit anchor --org <id>` writes the day's anchor now.
- `verify --org <id> --anchors` (blob store from the `SSC_BLOB_*` settings) lists the bucket, then from one REPEATABLE READ snapshot compares every row and every object with the chain, printing each problem as `anchor <cause>: <key> seq <n>`: `mismatch` (the chain's hash at that seq differs: rewritten history), `ahead` (the anchor is beyond the head: lost events), `missing` (a row without its object), `malformed`, `differs` (row and object disagree) and `stale` (no anchor object in the last 36 hours, counted from the org's creation when it has none). It exits 0 only when the chain and every anchor hold.
- Supersession: a restore anchor written at time A for a restore to T supersedes every anchor with `T < anchored_at < A`; those witnessed events the restore lost and are counted as superseded, not checked. An anchor written at or before T witnessed only events committed before T, so it must still agree.
- Point-in-time restore, before the API and the worker serve again: restore to T; for every org (ids from `ssc.org_index`) run `python -m ssc_control.audit reanchor --org <id> --restored-to <T, RFC 3339 with offset> --ref <ticket>`. It refuses and writes nothing (exit 1) unless `verify` passes and every anchor written before T agrees with the chain (a disagreement is tampering or the wrong T: stop and investigate). Otherwise, in one transaction, it writes a `restore` anchor with `restored_to = T` and appends `audit.reanchored` (target `audit_anchor`, the object key; `after`: `restored_to`, `prior_anchor_seq`, `head_seq`, `ref`). A daily job for a day the restore lost finds its object superseded and returns the restore anchor.

- Amendment 2026-10-03 (SSC-012): each org's anchors live in its cell's bucket. In code with local tests; not yet run in a cell.
  - Where: `storage.org_store` makes one choice for an org's snapshots and its anchors: the bucket `SSC_CELL_BUCKET_TEMPLATE` names for the org's `cell_label` when the template is set, else the `SSC_BLOB_*` store. It was `snapshot.service.published_store`, moved unchanged so both callers share it. The worker always has the template (`infra/ssc_infra/control.py` `worker_env`), so in a deployed stage anchors go to `ssc-c-<label>-cell`. The anchor tick and job do nothing only when neither store is set.
  - Layout: unchanged keys, `audit-anchors/<org>/<YYYY-MM-DD>.json` and `audit-anchors/<org>/restore-<YYYYMMDD-HHMMSS-ffffff>.json`, beside `snapshots/<org>/…` in the same bucket. Nothing else writes the cell bucket, and neither prefix is the other's start, so they cannot collide.
  - The command line: `python -m ssc_control.audit` runs with the worker's settings (`SSC_DATABASE_DSN`, `SSC_BLOB_*`, `SSC_CELL_BUCKET_TEMPLATE`) and resolves each org's store the same way, so `verify --anchors`, `anchor` and `reanchor` read and write where the job does. It exits 2 only when neither store is set, and prints `no such org: <id>` and exits 1 for an org that does not exist (`test_an_unknown_org_is_one_line_and_exit_1`). Before this change it read only `SSC_BLOB_*`, so with the worker's settings it looked in the control plane's blob bucket and would have reported every cell-bucket anchor `missing`.
  - Anchors already in the old store: none exist outside tests, so nothing is moved and no migration tool is written. A row whose object is only in the old store is reported `missing` by `verify --anchors`; that is the right answer, since the store the job writes to does not hold it. `ssc.audit_anchor` records no bucket name, so a later move of an org to another cell needs its anchors copied with it (placement's ticket).
  - Who can change anchors: the worker only. On the cell bucket only the control plane's worker (`bucket-control-worker`) holds `storage.objectUser`. The API's grant there (`bucket-control`) is removed: no API code reads or writes a cell bucket (its one store is `SSC_BLOB_*`, and snapshot confirmation runs in the worker). The gateway and the agent hold `storage.objectViewer`; no other cell account holds a storage role, and no cell custom role holds a `storage.` or `resourcemanager.` permission (`infra/tests/test_cell.py`, `test_only_the_worker_may_change_objects_in_the_cell_bucket`). The agent may act as any account in the cell project (`iam.serviceAccounts.actAs` on the project, for Cloud Run and builds), so a Google default account holding `roles/editor` would also reach them. The cells folder now enforces `iam.automaticIamGrantsForDefaultServiceAccounts` (`policies.cell_rules`), so a new cell project's default accounts get no such grant; the policy does not remove a grant made earlier, so the proof run still checks the project's IAM policy (`infra/README.md`). The operator's just-in-time `roles/writer` on the cells folder can also change them. Versioning is on, but `objectUser` may delete a noncurrent generation too, so until Step 5 someone who holds the database owner role and the worker's account can still rewrite history unseen.
  - Step 5, not built: a bucket retention lock cannot cover one prefix, and it would stop `latest.json` being replaced, so it cannot be set on the cell bucket. The lock is either per-object retention (Object Retention Lock, set on each `audit-anchors/` object as it is written, with `storage.objects.overrideUnlockedRetention` held by no SSC account) or a separate locked anchor bucket per cell, which `org_store` would name instead. The `audit-anchors/` prefix keeps both open.
  - Restore: `reanchor` takes the store from `org_store`, so a point-in-time restore writes its restore anchor to the cell bucket and checks the cell bucket's anchors (`test_reanchor_after_a_restore_writes_to_the_cell_bucket`).
  - Tests: `test_the_tick_anchors_each_org_in_its_own_cell_bucket` (two orgs, two buckets, nothing in the blob store, only `audit-anchors/` keys), `test_the_cli_uses_the_orgs_cell_bucket_with_worker_settings` (with and without `SSC_BLOB_*`; an old-store anchor reported `missing`). Live checks: `infra/README.md`, Audit anchors.

Reason: the log is the evidence customers and auditors rely on after something goes wrong, so its bytes must be reproducible by anyone, forever, from the export alone. Freezing the canonical form before the first export is cheap; changing it after would split every chain. The views keep personal data and secrets out of a table that can never be edited, and serialising appends on one head row keeps the chain linear under concurrent requests without a sequence or advisory lock.

Reverse if: an org's append rate makes the single head row a bottleneck (then per-org chains are split into dated segments linked by their first `prev_hash`, as a v2), a regulator requires the client IP inside the evidence (then the IP rule is revisited with SSC-013 before any IP is written), or a day between anchors is too long a window for undetected rewriting (then the tick writes an anchor per hour under an hourly key, a v2 key scheme beside v1).

## 013 Manifest v1 and the blob store protocol

Choice: an app asks the platform for everything through one file, `ssc.toml` with `schema = "ssc/v1"`. Contract in `docs/contracts/manifest.md`; code in `ssc_contracts.manifest`, `ssc_contracts.capabilities` and `ssc_shared.canonical`. Blobs go through one protocol, `ssc_shared.blobstore.BlobStore`.

- A manifest is a request, never enforcement. Asking for an ungranted Postgres, connection or egress host still deploys and prints the capability diff (severity, one fixed sentence, approver); `blocks` is always false. An invalid manifest is refused with every problem listed as `ssc.toml:LINE:COL: field: message`.
- Strict: one TOML type per key, no coercion, unknown keys refused with a suggestion. A present file must say `schema = "ssc/v1"`; a missing file is `default_manifest()`.
- Public build values are per environment (`[build.public_env.prod]`, `[build.public_env.preview]`). Only `VITE_*`, `NEXT_PUBLIC_*` and names listed in `build.public_names` are allowed; secret-looking and platform-set names are refused. Amendment 2026-10-03 (SSC-093): names starting with `RAILPACK_` are platform-set too, because public build values reach `railpack prepare` as `--env` and a `RAILPACK_*` name there would change the build itself (the system packages it installs, among others).
- Postgres is the only state. A key-value request is refused with the fix-it `STATE_KV_UNSUPPORTED` (a table, or an `UNLOGGED` table for a cache).
- Class names are v1 data; their sizes are platform policy outside the digest (decision 014). `sessions = true` caps an app at 1 instance.
- Schedules carry what `ssc_control.ports.DeclaredSchedule` reads: `name`, `cron`, `timezone` (default `UTC`), `path`, `method` (default `POST`), `timeout_seconds` (default 60, at most 900). Cron is checked in pure Python so contracts stay pydantic-only; tests cross-check it against `cronsim`.
- Digest: `sha256:` over RFC 8785 canonical JSON of the normalised model (defaults applied, lists sorted, cron spacing and name case normalised). Comments, order and quoting never change it. RFC 8785 is for manifest, snapshot and bundle digests only, never the audit chain (decision 012).
- `BlobStore`: `put` (optionally checked against a size and sha256), streaming `get`, `stat`, `list` by key prefix, `signed_url` for `GET` or `PUT`. Keys are lower-case `/`-separated segments. `FsBlobStore` writes one file per object with a fixed 512-byte header, atomically, and checks size and sha256 on every read. Every implementation runs `conformance/ssc_conformance/contracts/blobstore.py`. Signed-URL policy and the bundle key layout are decision 015.
- Amendment 2026-09-29 (SSC-014, B6): `BlobStore.delete(key) -> bool` removes that one key (`key/...` stays) and answers False when there was nothing to remove; the contract suite covers it. Its only caller is the bundle collector (decision 015).

Reason: the manifest is the contract between the CLI, the control plane, the doctor and the reconcilers, and B3, B4, A4, A5 and C1 all read it, so its key set, refusal format and digest are fixed first. A request-never-enforcement model lets a builder deploy before an admin decides, while the diff keeps the gap visible. Digesting the normalised model rather than the text means reformatting a file never looks like a change. A single blob protocol with a contract suite lets the cloud bucket arrive later (SSC-013) without touching callers.

Reverse if: a change would refuse or re-digest a manifest v1 accepts (then `ssc/v2` is added beside v1 and `load_manifest` dispatches on `schema`), a customer needs a key-value store the Postgres fix-it cannot cover (then a `[state]` key is added in v2 with its own decision), or the chosen cloud cannot honour exact length and sha256 on a signed upload (then decision 015 records the weaker binding and the contract suite marks it).

## 014 Runtime driver and worker

**Amendment pending (decision 025, 2026-10-03).** In code since SSC-017 reopened, not yet proved in a cell: the warm rule is deleted from `desired_for`, so every environment is minimum 0 (the org's warm flag is SSC-092). `ServiceSpec` gains `billing`, `timeout_seconds` and `concurrency`, set by `desired_for` from `is_session_app` and never from the manifest: a session environment is `instance` (`cpuIdle: false`) with 3600 s and 1000 requests per instance (its one instance holds every user's WebSocket), any other `request` (`cpuIdle: true`) with 300 s and 80. A fifteenth probe, `cannot_reach_peer_cell`, reports skipped (`no peer cell`) without a second cell. With one, a 404 passes only when neither the peer probe app (asked on `/health`) nor the peer gateway (on `/.ssc/logout`) can have sent it, and the direct-range leg is recorded as not applicable (same range, separate networks) when the peer's range holds the prober's own address; separate networks are enforced by `compute.restrictVpcPeering` (SSC-095). Choice: the control plane reaches a container runtime only through `ssc_control.runtime.driver.RuntimeDriver`, and runs every background job in one Procrastinate worker, `python -m ssc_control.worker`. `FakeRuntimeDriver` (`runtime/fake.py`) implements the protocol until the Cloud Run driver arrives with a cell (SSC-001, SSC-013). Every implementation runs `conformance/ssc_conformance/contracts/runtime_driver.py`.

- Protocol: `apply(spec) -> revision` creates or updates the service and returns the revision for the spec's fingerprint, reusing an existing one; it never moves traffic (except a new service's first revision, which is all there is to serve), sets scaling and labels, and clears `stopped`. `set_traffic(service, revision)` sends 100% to one revision. `scale_to_zero(service)` serves nothing and keeps revisions. `observe(service)` returns the revisions (fingerprint, digest, ready, failed, traffic), scaling and `stopped`, or None when there is no service.
- `ServiceSpec`: service `ssc-a-` plus the environment id's 20 characters; image by `sha256:` digest only (a tag is refused when the spec is built); port and health path from `[runtime]`; resource class; env; min and max instances; labels `ssc-org`, `ssc-app`, `ssc-env`. `spec_fingerprint` (`ssc-spec-v1`, sha256 over sorted JSON) covers image, port, health path, vCPU, memory and env. A driver computes it from a revision's actual configuration, never from a label it wrote, so drift in any of those shows. Scaling and labels are service settings outside it.
- `desired_for(env, release, manifest, app_status, framework)` is pure. A disabled or quarantined app gives `Stopped`. Min instances is 1 for `prod` when the manifest asks for Postgres, a connection or an internet host (the private network path can take a minute after a cold start), else 0. Max instances is 1 for `sessions = true`, for a session framework the build detected (`streamlit`) and for a start command naming one, and for `postgres = true` (SSC-040: the login role's second connection stays free for the next revision); else the class limit.
- Resource classes, in `ssc_contracts.manifest.RESOURCE_CLASSES` (sizes are platform policy outside the manifest digest, decision 013): `small` 1 vCPU, 512 MiB, at most 2 instances; `medium` 1 vCPU, 2 GiB, 4; `large` 2 vCPU, 4 GiB, 8. Revisit after SSC-001 cost data.
- App environment names are fixed in `ssc_contracts.app_env`: `PORT`, `HOME` (always `/tmp`; the root filesystem is read-only), `DATABASE_URL` (SSC-026) and its parts `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`, `PGSSLMODE`, `PGSSLROOTCERT` (SSC-040), `SSC_APP_ORIGIN` (the identity note's audience) and `SSC_IDENTITY_KEYS_URL`. A manifest can set none of them. The spec sets `PORT` and `HOME`, the database variables with `[state] postgres = true` (SSC-040), and on every app, as plain values, `SSC_IDENTITY_KEYS_URL` (the worker's `SSC_IDENTITY_JWKS`, the cell's stack output `identity_jwks`, compacted into a `data:` URL) and `SSC_APP_ORIGIN` (`https://<slug>[--preview].<label>.<apps domain>`, the label from `SSC_IDENTITY_ISSUER` = `https://keys.delimitus.com/<label>`, one cell as for `SSC_CELL_AGENT_URL`; SSC-018). Each is left out while its setting is unset. They are in the fingerprint without a new `FINGERPRINT_VERSION`, so when a setting appears or changes the reconciler sees every running app as drifted and rolls it to a new revision.
- Reconciler (`runtime/reconciler.py`), first match wins: desired `Stopped` gives nothing when the service is missing or already stopped, else `scale_to_zero` (a disabled app is never created or restarted); a missing service, no revision matching the fingerprint, a stopped service or different scaling gives `apply`; a matching revision that is not ready gives a wait (`revision_failed` when it never will be); traffic not all on it gives `set_traffic`; otherwise converged. One change per pass. Any state converges within two changes, so the third pass sees nothing to do (a property test). Desired state is read in a short `bound_org` transaction that commits before the runtime is called: the live pointer, its release, the release's manifest through the `ReleaseSpecs` port, and `app.status`. Until B3 stores manifests the port has none, the outcome is `no_spec` and nothing changes.
- Jobs (`runtime/jobs.py`): `runtime:reconcile_tick` runs every 15 seconds (cron `* * * * * */15`), reads `ssc.org_index` (decision 009 amendment), and in each org's bound transaction defers `runtime:reconcile_env` for every environment with a live deployment, with `queueing_lock` `reconcile:<env id>` (at most one waiting pass) and `lock` `env:<env id>`. Every job of any lane that calls the runtime driver for an environment takes that same `env:<env id>` lock, so they run one at a time. Worst-case repair: three passes, 45 seconds.
- Worker (`worker.py`): one `App` over `PsycopgConnector` with the `ssc_app` DSN plus `-c search_path=procrastinate` (`queue_conninfo`). Each lane adds one `add_tasks_from(<factory>(), namespace=<lane>)` line in `build_app`; blueprints come from factories because `add_tasks_from` renames the tasks it copies. Tasks declared with `pass_context=True` get the `Ports` (engine, runtime driver, release specs, blob store, snapshot, timers, prod gate, clock) from `additional_context` through `worker_ports.ports_of(context)` and never build their own clients. Heartbeat every 5 s, `stalled_worker_timeout` 30 s, polling every 5 s; succeeded jobs are deleted (a 15-second tick would otherwise grow the table forever), failed jobs kept.
- Stalled sweep (decision 008): `core:stalled_sweep` runs every 30 seconds, `get_stalled_jobs(seconds_since_heartbeat=30)` then `retry_job` for each. `WorkerSettings` refuses a stall threshold that is not above two heartbeats. Every task must be safe to run twice.
- Deferring: `ssc_control.deferral.defer(conn, task_name, *, queueing_lock, lock=None, queue=None, schedule_at=None, priority=None, **kwargs)` writes the job through the caller's SQLAlchemy connection, inside its open transaction (refused otherwise), in a savepoint. The savepoint sets `search_path` to `procrastinate` for the insert and restores it, so the API's engine keeps its own path. A duplicate `queueing_lock` returns None and leaves the transaction usable. Tasks are named by string (`"<namespace>:<task>"`); the API never imports `ssc_control.worker` or `runtime.jobs` (an import-linter contract).
- Composition: `SSC_DATABASE_DSN` is required. `SSC_RUNTIME_DRIVER` unset means no driver (the tick defers nothing); `fake` selects `FakeRuntimeDriver` and is refused unless `SSC_ENV` is `dev` or `test`; any other value is refused. `main` exits 2 on a composition error.
- Upgrading Procrastinate: a new revision applies that release's `sql/migrations/*.sql` the way `0006_procrastinate_orgindex` applied the vendored `schema.sql`. The vendored file never changes; a test pins it to the installed package.
- Probes (`conformance/ssc_conformance/runtime_probes.py`): fourteen. `non_root_10001`, `listens_on_PORT`, `health_path` and `no_write_outside_memory` run locally against the probe image (`conformance/runtime/probe_app/`, `python:3.14-slim` by digest, `USER 10001`) under `--read-only --tmpfs /tmp`. The other ten report `skipped: needs a staging cell (SSC-006 cloud choice, SSC-013 cell bootstrap)` and can never pass.

## 015 Source bundles

Choice: a deploy uploads its source once, as a deterministic `.tar.gz` (`ssc_bundle.pack`), to the blob store through a signed URL, and the control plane stores it only after checking the stored object itself. The client packs and scans (`ssc_bundle.client`); the server trusts neither. Checks in `ssc_control/deploy/bundles.py`, API in `api/routes/v1/bundles.py`, table `ssc.bundle` (revision 0008).

- Flow: `POST /v1/apps/{app_id}/bundles` `{digest, size_bytes, source_commit?}` records a `pending` row and answers `201` with `upload` `{method: PUT, url, headers, expires_at}`. The same digest again answers `200`: a stored bundle with `upload: null`, a pending one with a fresh URL. A different `size_bytes` for a recorded digest is `BUNDLE_DIGEST_MISMATCH`. `POST .../bundles/{id}/complete` runs the checks and stores the bundle, auditing `bundle.stored`; a stored bundle answers `200` again with no second audit (the store is a conditional update of a `pending` row, so two racing completes audit once). `GET .../bundles/{id}` reads one. Callers: an active org admin, the app's owner, or a builder on any of the app's environments, with a user credential; workload and integration credentials are refused until a ticket needs them. A disabled or quarantined app takes no new source (`APP_NOT_ACTIVE`).
- Keys: `bundles/{org_id}/{app_id}/sha256/{hex}.tar.gz`, content-addressed per org and app, so the same bytes are one object and one row (`UNIQUE (org_id, app_id, digest)`). A row is `pending` until `complete`, then `stored` with the manifest read from the bundle, its digest (decision 013) and the file count; `bundle_stored_check` allows only those two shapes.
- Signed URLs (decision 013): at most 10 minutes, HMAC-SHA256 over method, key, expiry, length and sha256, with the key id in the URL so keys rotate. A PUT stores exactly the signed length and sha256 and stops reading at the length (`BUNDLE_TOO_LARGE`, `BUNDLE_DIGEST_MISMATCH`). A tampered, wrong-method, expired or repeated-parameter URL is `UPLOAD_URL_INVALID` (403). The URL is a credential, and the idempotency layer stores the POST's body with it, so a replayed POST can answer with an expired URL; the client then posts again with a new `Idempotency-Key`.
- The filesystem store (`SSC_BLOB_BACKEND=fs`) runs in dev and test only: `create_app` refuses it unless `SSC_ENV` is `dev` or `test`. The API serves its URLs at `/blobs/{key}`, outside the OpenAPI document and mounted only for that store, and stores and serves every object as `application/octet-stream` with `Content-Disposition: attachment`, `nosniff` and `no-store`. Deployed cells use the bucket's own signed URLs, bound the same way, behind the same `BlobStore` protocol (SSC-013). Without a store (`none`, the default) the bundle endpoints answer `INTERNAL`.
- Checks at `complete`, in order: the stored object's size and sha256 (`BUNDLE_NOT_UPLOADED`, `BUNDLE_DIGEST_MISMATCH`); the compressed cap; a read-back hashed while it is copied to a temporary file; the tar rules of `ssc_bundle.tarcheck` (gzip over one tar with no non-zero byte after its end; regular files and directories only; relative NFC names with no empty, `.` or `..` part and no backslash; no duplicates; no `.env*` file at any depth; bounded extended headers; the file and unpacked caps checked from each header before its data is read), refused as `BUNDLE_MALFORMED` or `BUNDLE_TOO_LARGE`; `ssc.toml` from the bundle (none gives the default manifest, invalid gives `MANIFEST_INVALID`, the code name `ssc doctor` uses); the secret scan again, with the manifest's declared public values allowed (`SECRET_IN_BUNDLE`). Evidence goes to the log only: paths, lines, fields and rule names, never a value, masked or not, and never a manifest message.
- Caps, adjustable in settings: 100 MiB compressed, 500 MiB unpacked, 20,000 files.
- Releases: a release built from a bundle carries `source_digest` equal to the bundle digest (B4). `BundleReleaseSpecs`, the worker's `ReleaseSpecs`, and `release_manifest`, an approvals `ManifestLoader`, read the stored manifest joined on that digest and re-derive its digest. A missing or pending bundle, or a manifest that does not hash to `release.manifest_digest`, reports `no_spec`, so an edited row can never change what runs.
- Not yet: `complete` holds its request transaction open while it checks, bounded by the caps.
- Amendment 2026-09-29 (SSC-014, B6): the bundle collector and one store factory.
  - `deploy:collect_bundles` runs hourly (minute 17) over `ssc.org_index` (`deploy/bundle_gc.py`). It lists `bundles/{org}/` and deletes an object older than 24 hours when its row is `pending` and also older than 24 hours, or when no row names it. It never deletes a `stored` bundle's object, an object whose digest a release of that app carries (whatever its row says), or a key that is not a bundle key. Rows are never deleted (`ssc.bundle` has no DELETE grant): the same digest again answers a fresh URL. One org's failure is logged, the others are collected, and the job then fails so the failure stays visible. With no store it does nothing.
  - Each decision and its delete share one transaction. It holds the key's advisory lock `(15, hashtext(key))`, which `POST .../bundles` takes before it records a digest, and the row `FOR UPDATE`, which `complete` takes before it reads the object. The collector only tries (`pg_try_advisory_xact_lock`, `SKIP LOCKED`): what another transaction holds waits for the next run. It re-reads the object just before the delete and keeps it when it is now younger than 24 hours (written again since the listing). Left open: a client holding a URL issued before the collector's lock whose PUT lands between that re-read and the delete loses the upload; `complete` then answers `BUNDLE_NOT_UPLOADED` and the client uploads again. Temp files of a crashed filesystem write are not collected.
  - `ssc_control.storage.blob_store` is the one factory. The API (`api.routes.blobs.blob_store_for`, over `Settings`) and the worker and operator commands (`blob_store_from_env`) both call it, so one configuration gives one store or one `StorageConfigError` everywhere.

- Amendment 2026-10-01 (SSC-014): the bucket's own signed URLs.
  - `SSC_BLOB_BACKEND=gcs` is the bucket `SSC_BLOB_BUCKET`. Its URLs are V4 query-signed XML API URLs, signed by `ssc_shared.blobstore_gcs.v4_url` with the store's clock. The signature comes from IAM `signBlob` as `SSC_BLOB_SIGNER`. For the control plane that is its own account, which holds Token Creator on itself (`control-staging-signs-urls` in the platform stack); no key file exists. A test checks that the output is byte for byte what `google-cloud-storage` signs. One bucket per control deployment until placement (which cell holds an org) has its ticket, as for the runtime driver (SSC-017).
  - A PUT URL signs these headers, so a request without exactly these values is refused:
    - `x-goog-content-length-range: n,n` (the exact length)
    - `x-goog-meta-sha256` (what `stat` reports)
    - `x-goog-if-generation-match: 0` (create only, so a stored bundle cannot be replaced later through a URL still within its 10 minutes)
    - `content-type: application/octet-stream`

    A bucket PUT URL therefore needs the sha256.
  - GCS does not hash the body of a signed PUT: a signed `x-goog-content-sha256` that differs from the body is accepted (200), checked live 2026-10-01 by `conformance/tests/test_blobstore_gcs.py::TestGcsSignedUrlsLive` (`SSC_TEST_GCS_BUCKET`, `SSC_TEST_GCS_SIGNER`), so the URL does not sign it. The sha256 is checked when the object is read: `complete` re-reads it, and `get` hashes it range by range against the recorded sha256 (`BlobCorruptError`), so wrong bytes never become a stored bundle. This is the weaker binding decision 013's reverse-if clause names; the contract marks it with `url_checks_sha256 = False`, which accepts "stored, then corrupt on read".
  - `complete` deletes an object that is not the declared bytes (`BUNDLE_DIGEST_MISMATCH`), because a create-only URL could not replace it. The row stays `pending`, and the next `POST .../bundles` answers a fresh URL.
  - `ssc deploy` sends the exact `Content-Length` (never chunked) and treats `412` from the upload target as "an object is already there", going on to `complete`, which decides.
  - The bucket store's `get` reads 8 MiB ranges pinned to one generation, so a 100 MiB bundle is not held in memory.

Reason: the client is the customer's machine or agent and can be changed, so the server repeats every check on the bytes it stored. Content addressing makes a retried deploy free and lets a release name its source by digest. Binding the URL to the length and sha256 means a leaked URL can upload only the bytes already declared, within 10 minutes. Reading the manifest from the stored bundle, and checking its digest on every read, ties what is approved and run to the uploaded bytes.

Reverse if: SSC-013's bucket cannot bind a signed PUT to a length and sha256 (then the checks at `complete` remain the guard and this decision records the weaker binding), large bundles make `complete` too slow for one request (then it becomes a job that marks the row), or the GitHub App path (SSC-047) fetches source server side (then the row gains a source kind).

## 016 Approvals

Choice: a change that needs a person's approval becomes an `ssc.approval_request` for one question, `(environment, kind, subject_key)`, decided by another active admin of the org and recorded by SSC staff until SSC-049 ships the inbox. Rules in `domain/approval_rules.py` (pure, typed); service, gate and capability sources in `ssc_control/approvals/`; API in `api/routes/v1/approvals.py`.

- Kinds: `connect_data_source` (subject: the connection name), `enable_internet_hosts` (the host), `widen_audience` (a `sha256:` digest of the whole desired grant set) and `agent_share` (a digest of the desired set and the `grants_version` it replaces). The `approval_request_kind_check` CHECK and `RequirementKind` list the same four; a test compares them.
- One open request per question (partial unique index `approval_request_one_pending`). Asking again while one is pending or approved returns it (`POST /v1/approvals` answers 200, not 201); after a denial or a withdrawal a new request is opened. The newest request answers the question.
- Approver: an active org admin other than the requester, never in an agent session. Checked in that order (agent session, self, eligibility) by `check_decider`, and again by the database: `approval_request_not_self` (now covering denials as well as approvals; 0001's unnamed CHECK covered approvals only) and `approval_request_decided_via_agent_check`. The approver's `user_account` row is locked `FOR SHARE` so they cannot be demoted or deactivated mid-decision. The requester may still cancel their own request (no endpoint yet; SSC-049).
- Recording: `POST /v1/approvals/{id}/decision` takes an operator credential only (`PrincipalKind.OPERATOR`, no agent claim), with `{outcome, approver_user_id, channel: email|chat, reason}`. It stores `recorded_by_operator` (the operator credential's subject, an opaque staff id), writes a `policy_decision` (principal `user:<approver>`, action `approval.decide`), updates the row, and audits `approval.decided` (actor: the operator, with the policy link) and `operator.access`. Operator reads of approvals audit `operator.access` too. Refusal order: not an operator `FORBIDDEN`, agent session `AGENT_SESSION_REFUSED`, missing `NOT_FOUND`, decided `APPROVAL_NOT_PENDING`, approver is requester `SELF_APPROVAL_REFUSED`, approver not an active admin `APPROVER_NOT_ELIGIBLE`. Operator tokens are minted only in development until SSC-013/019 issue them.
- Asking: `POST /v1/approvals` for the environment's builders, its app's owner and org admins, agent sessions included (`requested_via_agent` from the credential). Admins and operators list every request; others see their own; a request the caller may not see is `NOT_FOUND`.
- Production gate, `production_gate(conn, *, org_id, environment_id, capabilities, requested_by, app_id=None, release_id=None)`, fails closed: `clear` only when every rule was evaluated and every requirement is approved. A missing environment, an environment of another app, an unknown `environment.profile` or environment name, unknown capabilities (None) or an unknown capability kind, or a requester with no user behind it give `refused`. `preview` is `clear` and asks nothing. In `prod` each data connection and each internet host is a requirement: approved passes, pending waits, denied refuses, missing is opened as a pending request (audited as `operator` / `system:prod_gate`) and waits. Every outcome writes a `policy_decision` (action `deploy.production_gate`, allow only when clear). The request is written in the caller's transaction, so the deploy job must commit after `waiting`.
- `ApprovalsProdGate` implements `ports.ProdGate` for B4 and C3; `RefusingProdGate` stays for tests. The requester is the release's author when a user of the org wrote it (their agent flag carried over), else the app's owner. What a release asks for comes from a `CapabilitySource`: `ManifestCapabilities(load)` reads `[connections]` and `[egress]` from the release manifest through a loader B4 supplies once it stores manifests (`requested_by_diff` maps B1's capability diff instead, refusing an unmapped kind or a summarised diff). Until then the default `RecordedCapabilities` treats the environment's approval requests (newest per question, not withdrawn) as its declarations.
- Profiles: `environment.profile` (default and only value `internal`, CHECK-limited). A new profile adds its rules to `approval_rules` and widens the CHECK in the same revision; until then the gate refuses it.
- Sharing (`PUT .../grants`): widening means a new subject gains access or an org-wide grant is added. Widening a data-connected environment needs `widen_audience` for the exact desired set; "data-connected" means the environment's app declares a data connection (`RecordedCapabilities` until B4, then the running release's manifest; unknown counts as connected), until SSC-052 links connections. Every change made through an agent credential needs `agent_share` (lead default for D2), bound to the grants version so an approval covers one change once. An agent session gets `202` `{environment_id, grants_version, approval_ids}` and the requests are opened for it; a person gets `APPROVAL_REQUIRED` and asks with `POST /v1/approvals` (`widen_audience`, `payload.grants` = the desired set). Nothing changes until approved; the retried `PUT` then applies and links the approval's `policy_decision_id` from each grant event (the `agent_share` one when both apply). A `widen_audience` approval covers its exact set whenever it is applied again; narrowing never waits.

MCP `request_share` opens `agent_share` (the current grants with the subject's grant set, at the current `grants_version`) and `request_connection` opens `connect_data_source` on prod; neither writes grants, and there is no approve tool.

## 017 Command line tool

Choice: `ssc` is a Typer 0.27 application over httpx2 in `packages/ssc_cli`. A command is registered only once it works against the live API; `test_help_lists_exact_set` holds the allowlist.

- Commands now (SSC-022 steps 1 and 2): `whoami`, `token set`, `token clear`, `apps`, `apps create`, `status`, `share`, `unshare`, `doctor`, `init`, `deploy`, `releases`, `rollback`, `promote` (SSC-042); since added: `mcp` (SSC-048), `requirements` and `policy` (SSC-093), `disable`, `enable`, `access explain` and `apps --mine` (SSC-022 C1c), `secret set` and `secret list` (SSC-026; no `secret get`, by design). `login` and `logout` (SSC-019, decision 024; `token set` stays for agents' and break-glass tokens). Later, when its endpoint exists: `logs` (SSC-024). `ssc deploy` always targets preview; production changes only through `promote`.
- Exit codes: 0 ok; 1 refused by the API or failed; 2 bad usage; 3 no token or 401; 4 blocked on this machine before anything was sent (`doctor` found a blocking problem, or `deploy` refused the folder); 5 network failure after retries. Usage errors are Typer's own: the message goes to stderr and there is no JSON, even with `--json`. The exceptions are `BAD_TOKEN_INPUT`, `BAD_API_URL`, `BAD_CONFIG`, `ENVIRONMENT_REQUIRED` and `SUBJECT_AMBIGUOUS`, which exit 2 with a JSON error.
- `--json` on every command prints one object on stdout with sorted keys. A failure prints `{"error": {...}}` on stdout with `code`, `title`, `detail`, `status`, `request_id`, `instance` and `type`. API refusals keep the problem's members. Failures found locally have `status: null` and one of `NO_TOKEN`, `NO_KEYCHAIN`, `BAD_TOKEN_INPUT`, `BAD_API_URL`, `BAD_CONFIG`, `NETWORK_ERROR`, `BAD_RESPONSE`, `APP_NOT_FOUND`, `ENVIRONMENT_NOT_FOUND`, `RELEASE_NOT_FOUND`, `ENVIRONMENT_REQUIRED`, `UPLOAD_FAILED`, `WAIT_TIMED_OUT`, `BUILD_FAILED`, `DEPLOYMENT_FAILED`, `DEPLOYMENT_SUPERSEDED`, `USER_NOT_FOUND`, `GROUP_NOT_FOUND`, `SUBJECT_AMBIGUOUS`, `BUILD_NOT_FOUND`, `KILL_SWITCH_FAILED`, `LOGIN_FAILED`, `LOGIN_ENDED`, or a code the API would give for the same refusal (below). The shapes are append-only: fields are never renamed, removed or retyped. `packages/ssc_cli/tests/json_shapes.json` records every field and `test_json_shapes_are_append_only` enforces it.
- Client: each POST sends one `Idempotency-Key` and reuses it across retries. GET and POST retry transport errors and 5xx three times (0.5, 1 and 2 s); POST also retries `IDEMPOTENCY_IN_FLIGHT`. Any request gets one wait of `Retry-After` (capped at 60 s) after a 429. PUT is not otherwise retried, except that `share` and `unshare` re-read and re-apply after a 412 `PRECONDITION_STALE`, at most three times, and send nothing when there is nothing to change. Response models ignore unknown fields; `test_client_models_match_openapi` checks each field against `docs/api/openapi.json`. Every request sends `X-SSC-Source-Tool: ssc-cli` (SSC-028's source tool mix; already in the stored shape `[a-z0-9._-]{1,40}`).
- Sharing that needs approval (decision 016): a `202` makes `share` and `unshare` exit 0 with `changed: false`, the rules still in force and the approval ids in `pending` (`[]` otherwise); `APPROVAL_REQUIRED` exits 1 and, without `--json`, adds a `Fix:` line giving the `POST /v1/approvals` body (`widen_audience` with the same grants).
- Sharing refusals (decision 019): the API keeps the reasons for `VALIDATION_FAILED` and `FORBIDDEN` in its log, so `share` and `unshare` work out the `Fix:` line from the rules. For `VALIDATION_FAILED` it names each grant below its environment's floor (a new one: use `--role builder`; those stored before floors: one `ssc unshare` command naming all of them, plus the grants this command removes or replaces, since each blocks every change and `unshare` removes every subject it names in one write) and any repeated subject, else it states the floors. For `FORBIDDEN` it says who may change that environment's sharing. The CLI's floor table only explains; `test_the_floor_is_the_apis` keeps it equal to the API's. There is no owner grant, so the owner's own grants can be removed like any other. `unshare` reports as removed only the subjects that had a grant and names the others as having none.
- Naming who to share with (SSC-021): `share` takes one of, and `unshare` one or more of, a `usr_` or `grp_` id, `--org`, an email address (anything with an `@`) or a group name (anything else); `--group` reads every name as a group name, for a group whose name has an `@` or starts with `usr_` or `grp_`. An email goes through `GET /v1/users?email=` and a name through `GET /v1/groups?name=`, both matched whole ignoring case, and both checked here first against the API's own limits. Several people can share an address and several groups a name, so the command goes on only when exactly one fits and otherwise exits 2 with `SUBJECT_AMBIGUOUS` listing the ids. `share` passes over deactivated people, since a grant gives them nothing; `unshare` does not, so their grants can still be removed. No match is `USER_NOT_FOUND` or `GROUP_NOT_FOUND`. ## 019 Sharing rules and access snapshots

Choice: sharing rules live in the control database and reach the gateway as one published document per org, `ssc-snapshot/v1` (`docs/contracts/access-snapshot.md`), evaluated by one function, `ssc_shared.access.decide`, which the control plane's explain endpoint and the gateway (SSC-018) both call. Rules in `domain/grant_rules.py`; compile, publish and acknowledgement in `ssc_control/snapshot/`; directory sync in `ssc_control/directory.py`; table `ssc.access_snapshot` and `ssc.snapshot_ack` (revision 0009).

- Floors: prod takes `user` or `builder`, preview takes `builder` only (`grant_rules.FLOOR`). `PUT .../grants` refuses a grant below the floor, or two grants for one subject, as `VALIDATION_FAILED`. A stored grant below the floor (written before floors) counts for nothing: `decide` answers `below_floor`.
- Who may change sharing: an active org admin, the app's owner, or a builder on that environment, with a user credential (`authz.require_builder`); `FORBIDDEN` otherwise. The check is per environment, so a builder on preview cannot change prod. This is stricter than bundles' "builder on any environment" (`require_app_builder`, decision 015).
- `PUT .../grants` order: user credential, subject shape, environment (`NOT_FOUND`), who (`FORBIDDEN`), `If-Match` (`PRECONDITION_STALE`), floors and duplicates, the audience-ceiling hook (`grant_rules.audience_ceiling`, a no-op until SSC-052), approvals (decision 016), then apply, audit, `share` metrics events, and `mark_dirty` when the set of grants changed.
- Owner: no owner grant is created, and the owner may remove every grant. The owner keeps the right to change sharing through ownership, and reaches the app only through a grant, like everyone else; there is no owner or admin shortcut in `decide`. The database keeps an app from losing its owner: `owner_user_id` is NOT NULL and the owner's `user_account` cannot be deleted (foreign key). `OWNER_NOT_ACTIVE` applies only when an app is created for, or transferred to, an inactive member; deactivating an owner is allowed (directory sync is never blocked).
- Compile: one SQL statement reads environments with their app's status, grants, users and memberships, so the document is one consistent read under READ COMMITTED. Every environment is listed; `hosts` stays empty until host labels exist.
- Publish: `snapshots/<org>/v<version>-<digest12>.json` is written, then the version's row inserted, in one transaction; `latest.json` moves after commit and is re-read until it names the newest committed version. A rolled-back publish leaves an object no row or pointer names. The put is bounded at 20 s.
- Versions: `mark_dirty(conn, org_id)`, in the changing transaction, takes the org's advisory lock `(21, hashtext(org_id))` shared, defers `snapshot:compile` with `queueing_lock` and `lock` both `snapshot:<org>`, and returns `max(version) + 1`: the version that will contain the change. `publish` takes the same lock exclusively (`lock_timeout` 30 s) before choosing its version, so it starts only when every dirtying transaction has ended, and a change that arrives while a compile runs waits for it and then queues the next one. `SnapshotPort.request` is `mark_dirty`. User creation, a status change, a membership change, an app's creation and a changed grant set mark the snapshot dirty; a role, name or email change does not (the document has none of them).
- Confirmation: a cell reports its applied version in `POST /internal/v1/heartbeat`. `SnapshotPort.confirmed(org, version)` is true when the org's latest report is that version or later and came from the org's cell (every org has a cell label from revision 0011), or, since 2026-10-03 (SSC-025), when `latest.json` in the org's cell bucket names that version or later. The gateway runs on demand and sends no heartbeat, but it reads `latest.json` before it decides, so the pointer is what it will apply. The worker's `Snapshots` reads it from the store the compile writes to (`storage.org_store`). With neither, it is false. An unpublished version is `REFERENCE_NOT_FOUND`; a heartbeat from another cell is `FORBIDDEN`.
- Directory: `POST /internal/v1/directory/users` (by `(issuer, subject)`, never email), `POST /internal/v1/directory/groups` (by `directory_ref`) and `PUT /internal/v1/directory/groups/{id}/members` (replaces the set; unknown or foreign users `REFERENCE_NOT_FOUND`). Operator credentials only: a workload credential is an app acting for itself and must never manage people. Audited as `user.created`, `user.updated` (with `role` only when it changed), `user.deactivated`, `user.reactivated` and `group.synced` (`directory_ref`, `added`, `removed`). Demoting or deactivating the last active admin is `LAST_ORG_ADMIN` (SC002). Two first syncs of one identity racing end with one `ALREADY_EXISTS`; the directory retries.
- Explain: `GET /v1/apps/{app}/environments/{env}/access?user_id=` (the caller by default), for those who may change that environment's sharing. It compiles the org live (version 0) and runs the same `decide`, naming the deciding grants with the group's cached name, and returns the newest published version beside it.
- Who the caller is (A4b): `authz.active_role` is the one answer to "is the caller an admin", read from `user_account` on every request, so a directory change applies at once, not at the next token. `GET /v1/whoami` returns it as `role`: `admin` or `member` for an active user of the org, `null` for a workload or operator credential, a deactivated user or one unknown to the org; `require_admin` passes exactly when it is `admin`. The console shows admin screens on it; the server still enforces.
- Finding people (A4b): `GET /v1/users?email=` matches the whole address, ignoring case, and returns every match with id, name, email, role and status, deactivated people included, because email is display data and never a key (`db/PII.md`); callers act on the `usr_` id. Active org admins only (`require_admin`), agent sessions of admins included, as for audit search; a builder shares by id. No prefix or pattern search.
- The apps a builder may ship (A4b): `GET /v1/apps?builder=me` lists the apps `require_app_builder` allows (bundles and deployments): every app for an active admin, the apps the caller owns, and those with a builder grant on any environment, direct, through a group or org-wide; none for a deactivated user. One SQL statement (`authz.buildable_app_ids`) and a test that checks it app by app against `require_app_builder`. Any credential but a user's is `FORBIDDEN`; without the parameter the list is every app, as before.
- Finding groups (A4c): `GET /v1/groups?name=` matches the whole name, ignoring case, and returns every match with id, name and `member_count`, the group's active members. A group's name is cached display data and never a key; callers share with the `grp_` id. Allowed to those who may change some environment's sharing (`authz.require_sharer`): an active org admin, even with no apps, an app's owner, or a builder on any environment, direct, through a group or org-wide; a test checks it person by person against `require_builder` over every environment. Finding people by email stays admin-only.
- Gateway (SSC-018, decision 023): every request is decided on the newest view the cell holds, so a sharing change or deactivation takes effect within one compile plus one 2 s poll. An open WebSocket or event stream is closed as well, within about 3 s of the new snapshot (SSC-021, decision 023 amendment); the session cookie stays, and every request it carries is refused. A view no poll has confirmed for 5 minutes stops all admission.
- Not yet: revoke-now bypassing the coalesced compile; registering the directory sync in the control-plane worker (SSC-017; the sync itself is decision 024); cell fetch and bucket binding (SSC-013); the audience ceiling (SSC-052); host labels (C3, SSC-013); pausing a deactivated or revoked builder's timers (A5).
- Worker (A1b): the worker composes `Ports.blob_store` from the API's `SSC_BLOB_*` settings (`ssc_control/storage.py`; the filesystem store only in dev and test). `snapshot:stale_sweep` runs every five minutes and marks dirty each org with no published snapshot, or whose newest one differs from a live compile (by `content_digest`, revision 0011) or whose `latest.json` does not name it, so a compile whose retries ran out is redone without waiting for the next change. Rows from before 0011 have no digest, so each org is recompiled once after the upgrade.

Reason: explain and the gateway must never disagree, so there is one evaluator and explain runs it on the same compile the gateway will load (Delimitus kept one `decide` for the same reason). A published version never changes and a rolled-back one is never named, so a cell can cache by version and check the digest. The lock handshake gives each change an exact version to wait for, which approvals, revocation and the console need, without the lost update a dirty counter with a coalesced job has when the waiting job is claimed between a change and its defer. Prod sharing is the dangerous one, so rights to change it are per environment. Keeping the owner out of `decide` keeps one rule, "everyone needs a grant", on both sides, while the database guarantees the owner who may fix sharing always exists.

Reverse if: waiting for a running compile makes sharing changes too slow (then a fenced version table replaces the shared lock), whole-org compiles get slow (then per-app documents in a v2), an org gets more than one cell (then `snapshot_ack` is keyed by org and cell and confirmation needs all of them), or the founder wants owners always to reach their app (then v2 carries owners and `decide` gains that rule).

## 020 Timers

Choice: an app's schedules are declared in its manifest (`[[schedules]]`, decision 013), kept in `ssc.schedule` and fired by the worker; every run is a row in `ssc.timer_run` (revision 0013). Times in `domain/schedule_time.py`; rows, pauses and the `TimersPort` in `timers/service.py`; claim, dispatch and sweep in `timers/runner.py`; the tasks in `timers/jobs.py` (namespace `timers`); the API in `api/routes/v1/schedules.py`.

- Declaring: after a deploy (decision 014), `TimersPort.sync_schedules` makes the environment's schedules match the release's manifest by name: a new name is inserted, a changed definition (`cron`, `timezone`, `path`, `method`, `timeout_seconds`) is updated, a missing name becomes `deleted` (terminal, SC007; its runs are kept and the name may be declared again, `schedule_live_name`). Audited as `schedule.created`, `schedule.updated`, `schedule.paused`, `schedule.resumed` and `schedule.deleted` through the `schedule` view. The deploying user becomes every schedule's declarer (`declared_by_user_id`). An active schedule whose cron and zone did not change keeps its armed instant.
- Preview (Q4, answer A): only prod runs on its own. Preview schedules are stored paused (`preview`) and run only by hand, so one job does not send real mail twice.
- Time: cronsim reads the cron in the schedule's IANA zone, loaded from the pinned `tzdata` package (2026.4), never the host's zone files, so every worker computes the same instants. The next instant is the first one strictly after the later of the last scheduled instant and now: runs missed during an outage fire once, late, and the schedule then skips to the next future instant. At fall back a fixed wall time fires once, at its first occurrence, and an interval fires in both hours; at spring forward a skipped wall time fires once, when the gap ends.
- Firing: an armed schedule has `next_run_at` and one `timers:run` job deferred in the arming transaction with `schedule_at` the instant and `queueing_lock` `sch:<id>:<YYYYmmddTHHMMZ>`. A manual run (`POST .../runs`) inserts `timer_run(queued, manual)` and defers a job with `queueing_lock` `tmr:<run_id>` and priority 1, ahead of due scheduled runs. No timer job takes a `lock`: Procrastinate 3.10 holds a job behind an earlier one with the same lock even while the earlier one waits for its `schedule_at`, and no timer job calls the runtime driver, so none needs `env:<id>`. Job arguments are ids and the instant only.
- Running: the claim runs in one org-bound transaction holding the schedule's row lock. A scheduled job is stale, and leaves no row, unless the schedule is `active` and armed for exactly its instant (so a paused, deleted or re-armed schedule's job does nothing); a manual job is stale unless its run is `queued`. Otherwise the run is `skipped` (`owner_inactive` or `builder_access_revoked`, pausing the schedule; `app_inactive` while the app is disabled or quarantined; `overlap` while another run is running; `deleted` for a manual run of a deleted schedule) or `running`. Every claim that does not pause re-arms the next instant. Dispatch runs outside any transaction, once, in two requests (SSC-041, revision 0025): a start, `GET` the running release's `runtime.health_path` under 150 s (`START_SECONDS`), which wakes the gateway and the app at zero, then the call under `asyncio.timeout(timeout_seconds)`, so the timeout counts from the app's first answer. The outcome is `succeeded` (2xx), `failed` (`http_error`, `dispatch_error`, `start_failed` when the start got no answer, an error or 500 and up within its window, or `dispatch_unavailable` when the worker has no dispatcher) or `timed_out` (`timeout`), written with `start_ms`, `duration_ms` (the call alone) and a `timer_run` metrics event (`trigger`, `environment`, `outcome`, `start_ms`, `duration_ms`). The real dispatcher (`timers/https.py`, `SSC_TIMER_DISPATCHER=https` with `SSC_TIMER_SIGNING_KEY` and `SSC_TIMER_KEY_ID`) sends both to `https://<app host>` through the cell's load balancer and gateway, each with a schedule token bound to that one request (decision 023, SSC-041 amendment), and never follows a redirect. A task retry after the claim committed finds the run stale, so a dispatch happens at most once; a run left `running` past 150 s plus its timeout plus a minute is closed as `timed_out` (`abandoned`).
- No overlap: `timer_run_one_running` allows one running run per schedule and `timer_run_one_queued` one waiting manual run; `timer_run_once_per_instant` backs up "one run per scheduled instant". A second manual run while one waits or runs is `409 TIMER_RUN_IN_FLIGHT`.
- Authority (Q3, answer A): a schedule runs for its app's owner, as declared by a builder. It is paused `owner_deactivated` when the owner is not active, and `builder_access_revoked` when the declarer may no longer change the environment (`authz.require_builder`; `timers.service.may_build` is the same rule in SQL, and a test checks the two person by person). This is checked when a deploy declares, when the directory changes a user's role or status or removes group members, when `PUT .../grants` changes the grant set, when the worker claims a run, and by the sweep every minute, which also catches an owner transfer. A manual run is skipped when its requester has lost that right. Resuming (`POST .../resume`) takes a person who may change the environment, who becomes the declarer; so does the next deploy, which also resumes a schedule paused for authority once both have it again. This closes decision 019's "pausing a deactivated or revoked builder's timers".
- Kill switch (decision 014, SSC-025): the saga's last step calls `TimersPort.pause_for_kill`, which pauses the app's active schedules as `app_disabled` or `app_quarantined` and returns their ids for the run row; enabling calls `resume_after_kill` with those ids, which re-arms each one still paused for that reason, or pauses it for authority if its owner or declarer lost it meanwhile (the enabling admin is the actor). Manual and preview pauses are never touched; a deploy keeps kill pauses; resuming by hand is `409 SCHEDULE_CANNOT_RESUME` while the kill switch holds a schedule, while the app is not active, in preview and while the owner is not active.
- Pausing by hand (`POST .../pause`) turns any SSC pause into `manual`, so only a person resumes it.
- API: `GET /v1/apps/{app}/environments/{env}/schedules` (live schedules with their latest run), `GET .../schedules/{id}`, `GET .../schedules/{id}/runs` (newest first, paged by `before`), `GET .../runs/{run_id}`, `POST .../runs` (`202` with a `Location`, audited as `schedule.run_requested`), `POST .../pause` and `POST .../resume`, for those who may change the environment (`require_builder`). Schedules change only with a deploy.
- Sweep (`timers:sweep`, every minute, `queueing_lock` `timers_sweep`): per org, closes abandoned runs, marks manual runs queued for over an hour `skipped` (`abandoned`), pauses what lost authority, and defers again any armed instant more than a minute overdue (a lost job, a claim whose retries ran out).
- Lock order: app and environment rows, then schedule rows, then `user_account` rows, then `audit_head` last. Every schedule writer (going live, `sync_schedules`, pause, resume, manual runs, the claim, the kill switch) takes its row locks before its first audit append; a hook that runs after its audit takes schedule rows only with `SKIP LOCKED`.
- Wiring: the platform stack's `timer_key_id` makes the worker's `SSC_TIMER_SIGNING_KEY` secret and sets `SSC_TIMER_DISPATCHER=https` and `SSC_TIMER_KEY_ID`; each cell's `timer_jwks` is that key's public JWKS (`infra/README.md`). Unset, the worker takes `fake` in dev and test, and no dispatcher fails runs as `dispatch_unavailable`.
- Not yet: a live cold run against a cell; retries of a failed run; `timer_run` retention; the end-to-end "within one tick" of an enable.

Reason: a job per instant with `schedule_at` needs no scheduler process and survives worker restarts, and arming in the changing transaction means a rolled-back change arms nothing. Coalescing gives "at most one late run" instead of a burst after an outage, which is what a job that sends mail or rebuilds a report wants. Pinned zone data keeps two workers from disagreeing about an instant. At-most-once dispatch is the safe default when the app's handler may not be idempotent. Checking authority at declaration, at each hook, at claim and in the sweep means a missed hook delays a pause by at most a minute and never lets a run through.

Reverse if: builders need at-least-once runs with retries (then a retry policy per schedule and an idempotency key on the call), missed instants must each run (then a catch-up limit per schedule), per-minute sweeps over every org get slow (then a due-schedule index across orgs, or per-cell workers), or zone names the manifest accepts are missing from the pinned `tzdata` (then the manifest checks names against the same package).

**Amendment 2026-10-03 (SSC-028): where the usage numbers come from.** Every per-environment number comes from Cloud Run's own metrics in the cell's Cloud Monitoring, read by the cell agent; the gateway counts nothing. Cloud Run writes these metrics for every revision whether or not anyone asks, reading them sends nothing to an app (so it never wakes or bills one), they are the numbers the bill is made from (SSC-096 compares like with like), and they need no state in a gateway that scales to zero and can be stopped without a last write. Only counts and durations leave the cell: never a request, a path, a user id or an address.
- An **instance hour** is 3,600 seconds of `container/billable_instance_time` for the environment's service, summed per UTC hour. For a session app (instance-billed) that is the instance's whole life, the idle minutes before Cloud Run stops it included; for any other app it is the seconds spent starting and answering.
- A **session hour** is 3,600 seconds of session time. Session time is 60 seconds for each UTC minute in which a session environment (instance-billed, `is_session_app`) had at least one instance serving a request, read from `container/instance_count` with `state = active`. An open WebSocket or event stream is a request for as long as it stays open. A request-billed environment has no session hours.
- A **cold start** is one instance started, from `container/startup_latencies`: the count per minute and their mean start time. It is stored as one event per environment and minute with `count` and `duration_ms`. Percentiles count each start at its minute's mean, and are given only from 20 starts.
- **Reading.** One read per cell covers every `ssc-a-` service at once: three `timeSeries.list` calls summed per service by Monitoring, one page each for a 200-app cell. The worker's `metrics:usage_collect` runs at 20 past every hour. It reads the whole UTC hours that ended at least 15 minutes earlier, from the org's cursor (`ssc.usage_collection`), at most 6 hours per run. Calls per cell: 3 an hour, 72 a day, 2,232 in a 31-day month, against a default read quota of thousands a minute. Events are written with `dedup_key` set to the environment and window start (`usage_hour`, `cold_start`) or to the resource (`fixed_resource`), under a unique index, so a repeated or overlapping run writes nothing twice.
- **Fixed resources.** The step that makes a cell resource `ready` (database, egress, connections) writes one `fixed_resource` event in the same transaction, keyed by the resource.
- **Usage type.** The usage type is read after the fact from one UTC month and is never declared or used to provision anything. `session`: any session hour. Otherwise by instance seconds, from the bands in the architecture document §10.1 at one vCPU: `rare` up to 19,500 (the top of the rarely-used band); `heavy` from 262,800 (a tenth of a 730-hour month); `daily` in between.
- A6 holds: these numbers are for metrics and the cost view, never for charging.
- **Lane A must add** before events appear: the Monitoring API enabled on each cell project, the agent's service account allowed `monitoring.timeSeries.list` there, and `SSC_USAGE_SOURCE=monitoring` on the agent. Without them the agent answers `USAGE_NOT_CONFIGURED`, and the worker logs it and writes nothing.

Reverse the source if SSC-086 shows the active instance count does not stay above zero for an open WebSocket, or that startup latency is far from the wait a user sees. Then session hours and cold starts move to the gateway.
